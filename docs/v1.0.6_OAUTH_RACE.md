# v1.0.6 OAuth 轮询竞态根治报告

> 本文记录「没有待处理的登录请求」竞态 bug 的完整排查与修复过程。
> 这个 bug 折磨了多轮才定位，根因极隐蔽（async setInterval + 状态提前清理），
> 留档防止后续重构时重新踩坑。

---

## 一、现象

用户复现路径稳定：

1. OAuth 登录账号 A → 成功
2. 删除账号 A
3. **再次登录账号 A** → 弹出「没有待处理的登录请求」错误 toast，
   紧接着又弹「登录成功」

更糟的表现：

- **重启网关（点开关 stop/start，非重启应用）后第一次登录直接报错**
- 触发一次后，**后续每次登录都会复发**，直到关闭整个应用重开
- 重复登录同一个号必触发；登录别的号不触发（误导性很强）

关键观察：**关闭整个应用重开能好**。这指向「进程内内存状态被污染」，
而不是数据库或网络问题。

---

## 二、误导性的弯路

排查过程中走过的弯路（避免下次再走）：

| 假设 | 为何错误 |
|------|---------|
| 「重复登录同号」是账号本身问题 | OAuth 流程对所有账号一致，不可能是账号问题。真因是同号重复登录更容易触发某个时机 |
| 删除账号没清理 OAuth 状态 | delete_account 确实不碰 _pending_oauth，但每次 start_login 生成新 login_id，旧 pending 不影响新流程 |
| 前端 oauthTimer 没清干净 | startOAuthPolling 开头 clearInterval 了，且加了 _oauthSettled + loginId 双重 guard 仍复发 |
| 后端 _current_oauth_login_id 脏 | 前端轮询传的是自己的 loginId，不依赖后端这个字段 |
| 「重启网关就该释放内存」 | 用户说的「重启网关」其实是点开关（stop/start uvicorn），Python 进程没重启，模块级 dict 和前端 JS 变量都还在 |

## 三、根因（日志实锤）

加诊断日志后，抓到触发瞬间的关键序列：

```
[OAUTH] poll in=f3284f22 ... in_pending=True     ← 第 4 次轮询，pending 还在
[OAUTH] poll in=f3284f22 ... in_pending=False    ← 第 5 次轮询，pending 没了！
[OAUTH] poll -> ERROR 没有待处理的登录请求        ← 报错
[OAUTH] poll -> completed                        ← 紧接着又 completed
```

### 机制

`setInterval(callback, 1500)` 的 callback 是 `async` 函数。当某次
`session.get(url, timeout=15)` 卡住超过 1.5 秒（服务器慢、网络抖动），
**下一个 interval 触发时，旧 callback 还在 await，新 callback 已经启动，
两个 poll_token 并发执行**。

旧 `poll_token` 实现（`src/api/oauth.py`）：

```python
def poll_token(login_id):
    pending = _pending_oauth.get(login_id)
    if not pending:
        raise ValueError("没有待处理的登录请求")   # ← 竞态点
    ...
    if access_token:
        _pending_oauth.pop(login_id, None)        # ← 拿到 token 立即删
        return {...}
```

并发时序：

```
poll-A（慢）：进入 poll_token → session.get 卡住 → 服务器终于返回 token
              → 第 83 行 _pending_oauth.pop(login_id) 删掉 pending
              → 返回 token（即将 completed）

poll-B（并发）：1.5s 后被 interval 触发 → 进入 poll_token
              → 第 58 行 _pending_oauth.get(login_id) 返回 None（已被 A 删）
              → raise「没有待处理的登录请求」

前端：poll-B 的 error 先到 → 弹错误 toast + 关 modal
      紧接着 poll-A 的 completed 到 → 弹「登录成功」
```

### 为什么「重复登录同号」必触发

同一个号在服务器侧的授权流程更短（已授权过、cookie/会话复用），
服务器返回 token 更快。但这反而让 poll-A 和 poll-B 的时间窗口更容易重叠——
poll-A 刚拿到 token 准备 pop，poll-B 已经进入检查 pending。

### 为什么「触发一次后每次都复发」

这是误导性最强的现象。实际机制：

- pywebview 的 js_api HTTP bridge 对同一方法的并发调用可能不严格串行
- 一旦网络条件触发过一次并发，后续每次登录的 polling 都有可能再次并发
- 只有重启整个应用（Python 进程退出）才会重置一切

「点网关开关」只是 stop/start uvicorn，**Python 进程和前端页面都没重载**，
所以 `_pending_oauth`、`oauthTimer`、`_oauthSettled` 全部保留，问题持续。

## 四、修复（三层防御）

### 第 1 层：后端根治 —— poll_token 不再 pop pending（最关键）

`src/api/oauth.py`：

```python
# 旧：拿到 token 立即删 pending（并发竞态源）
if access_token:
    _pending_oauth.pop(login_id, None)
    return {...}

# 新：只返回 token，pending 留着，由 complete_oauth_and_save 统一清理
if access_token:
    return {...}
```

并发 poll 都能拿到同一个 token，**没有人因为 pending 被提前删而报错**。
这一层单独就足以根治「没有待处理的登录请求」。

### 第 2 层：登录完成后彻底重置状态

`src/gui/app.py` 的 `complete_oauth_and_save` 末尾：

```python
oauth_api.reset_pending()           # 清空所有 _pending_oauth
self._current_oauth_login_id = None
```

`src/api/oauth.py` 新增：

```python
def reset_pending():
    """清空所有待处理的 OAuth 登录。"""
    _pending_oauth.clear()
```

每次登录完成，状态机归零。下次登录从干净状态开始。

### 第 3 层：前端容忍单次误报

`src/gui/index.html` 的 `startOAuthPolling`：

```js
let noPendingStreak = 0;
// ...
} else if (r.error) {
  // 「没有待处理」容忍一次：可能是并发误报
  if (r.error.indexOf('没有待处理') >= 0 && noPendingStreak < 1) {
    noPendingStreak++;
    return;   // 不报错、不关 modal，等下一次 poll
  }
  // 连续 2 次才真正判定失败
  ...
}
```

即使后端因某种未预见的路径偶尔报这个错，前端容忍一次，
避免单次竞态误报把好的登录流程关掉。

### 配套：跨轮 guard

前端 `_currentOauthLoginId` + `_oauthSettled` 防止「登录→删除→再登录」时
旧轮的残留回调（闭包里的旧 loginId）被新流程「复活」后用失效 loginId 调 poll。

## 五、关联修复（同一批提交）

这次提交还顺手修了几个相关问题：

### 5.1 手机号去重失败

`src/storage/store.py` 的 `find_duplicate` 旧代码：

```python
if "@" in norm:   # ← 只有真实邮箱才匹配
    rows = conn.execute(...email匹配...)
```

用户的账号 email 字段存的是手机号（18775642907），没有 `@`，
**永远跳过 email 匹配**，只能靠 uid。OAuth 偶发没返回 uid 时去重失败。

修复：去掉 `@` 限制，手机号/昵称当 email 用时也匹配。

### 5.2 昵称被空值覆盖

`src/storage/store.py` 的 `upsert_account` 旧 `ON CONFLICT`：

```sql
nickname=excluded.nickname   -- 无条件覆盖
```

OAuth 二次登录接口偶发没返回 nickname 时，把已有的好昵称冲成 None，
卡片显示 unknown。

修复：信息类字段（nickname/email/uid/enterprise_*/domain）用
`COALESCE(NULLIF(excluded.X, ''), accounts.X)`，新值为空保留旧值。
凭证类字段（access_token 等）照常覆盖。

### 5.3 列表排序卡片飘走

`list_accounts` 旧排序 `ORDER BY last_used DESC`，但 `upsert_account`
每次都把 `last_used = now`，禁用/启用/刷新 token 后账号被顶到最前。

修复：改用 `ORDER BY created_at DESC, id ASC`，created_at 稳定不变。
前端 filteredAccounts 的当前调度号置顶逻辑不受影响。

## 六、教训

1. **async setInterval 是并发陷阱**：callback 是 async 时，interval 到点不会等
   上一次 callback 完成，直接启动新的。任何「状态提前清理」的代码都会被并发打穿。
   修复方向：要么状态只读不删（本案例），要么用锁串行化，要么用 setTimeout 递归
   代替 setInterval（保证上一次完成才排下一次）。

2. **「重启就好」要分清重启什么**：重启进程 vs 重启某个子服务（uvicorn），
   内存释放范围完全不同。排查时要确认「重启」具体指哪个动作。

3. **加日志胜过推理**：这个 bug 推理了多轮（前端 guard、loginId 比对、状态机重置）
   都没根治，加一行 `in_pending=True/False` 的日志立刻锁定根因。
   隐蔽竞态优先用日志实锤，不要纯推理。

4. **「只有某个账号出问题」通常是误导**：OAuth/登录这种统一流程不可能因账号而异，
   「某账号必触发」往往是因为该账号的某个特征（响应快/慢、字段缺失）刚好踩中时机。
