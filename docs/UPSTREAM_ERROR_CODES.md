# 上游错误码与限流机制（实测记录）

> 2026-08-19 排查实录。结论先行：上游存在**两类完全不同的 429**，网关目前只看
> HTTP 状态码一刀切，导致「单个模型限流」被误判成「账号额度耗尽」而疯狂切号。

## 一、上游错误的两层结构

上游 chat 接口（`https://copilot.tencent.com/v2/chat/completions`）的错误信息分两层：

| 层级 | 字段 | 语义 |
|------|------|------|
| 传输层 | HTTP 状态码 | 429 Too Many Requests 等，只表示「请求过多」这类粗粒度 |
| 业务层 | 返回体 JSON 的 `code` | 6004 / 14018 / 11140 等，**真正的业务语义在这里** |

一次失败 = 一个 HTTP 状态码 + 一个业务 code。**判定错误类型必须看业务 code，不能只看
HTTP 状态码**——同一个 429 携带 6004 和 14018 时含义完全不同。

## 二、已观测到的业务 code

| code | HTTP | 含义 | 观测来源 |
|------|------|------|---------|
| `0` | 200 | 成功 | 全库 3800+ 次 |
| `6004` | 429 | **单个模型**频率/额度限制（「使用量已超出频率限制……可切换其他模型继续使用」） | 日志 8 次，实测样本：16501302824 用 glm-5.3 |
| `6020` | 429 | **排队等待**（`queue.waiting.title`，模型级队列，含 `queue_position`/`queue_size`/`retry_after`/`estimated_wait`） | 实测样本：kimi-k3-1 全池排队，504 位 |
| `14018` | 429 | **账号额度已用尽**（「额度已用尽，请购买加量包」） | 实测样本：59115774 用 deepseek-v4-flash |
| `10001` | 400 | 今天已签到 | 日志 1 次 |
| `10085` | — | 请求不合法（缺身份头/UA） | `src/api/client.py` 注释，未在日志中观测 |
| `11140` | 403 | 封号 `request illegal` | 代码 + `tests/test_failover.py`，日志未见 |

### 6004 vs 14018 —— 两个都是 HTTP 429，但语义相反

| 维度 | 6004 | 14018 |
|------|------|-------|
| 含义 | 单个模型频率/额度限制 | 账号额度已用尽 |
| 作用范围 | 账号 × 模型（其他模型不受影响） | 账号（所有模型都无额度） |
| 返回体 | `{"code":6004,"msg":"...频率限制...可切换其他模型继续使用"}` | `{"error":{"data":{"code":14018,"msg":"额度已用尽...购买加量包"}}}` |
| 恢复方式 | 频率限制，约 1-1.5h 自恢复，或换模型 | 购买加量包 / 额度结算 |
| 正确调度 | **同账号换模型** | 切账号 / 探测 |

> 注意 14018 的嵌套结构：`{"error":{"data":{"code":14018}}}`，与 6004 的顶层
> `{"code":6004}` 不同。网关 `_classify_upstream_error` 已能正确解析出 14018。

## 三、6004 单模型限流的实测细节

### 返回体示例

```json
{"code":6004,"msg":"您的使用量已超出频率限制，将在 2026-08-20 01:35:44 UTC+8 重置，您也可以切换其他模型继续使用。","requestId":"..."}
```

### 特性（实测）

1. **按「账号 × 模型」独立计限**：账号 16501302824 的 glm-5.3 被限时，实测其它模型全部正常——
   | 模型 | 结果 |
   |------|------|
   | hy3 | ✅ 200 |
   | deepseek-v4-flash | ✅ 200 |
   | glm-5.2 | ✅ 200 |
   | kimi-k3-1 | ✅ 200 |
   | glm-5.3 | ❌ 429 code 6004 |
2. **频率限制，非 24h 硬性额度**：实测撞限后约 1.5h 内自恢复——16501302824 在 02:10:43
   撞 6004，03:47:10 用 glm-5.3 再次请求已成功（200）。消息里的「将在 08-20 01:35 重置」
   是每日用量计数窗口，**不代表持续限流到那个时间**。不同账号的重置时间互不相同，
   说明计限是逐账号独立窗口。
3. **提示语明示换模型**：「您也可以切换其他模型继续使用」→ 上游预期是**换模型**，不是换账号。

### 连锁切号的完整轨迹（2026-08-19）

| 时间 | 账号 | 6004 重置时间 |
|------|------|--------------|
| 02:10:43 | 16501302824 | 08-20 01:35:44 |
| 02:26:09 | 16299273893 | 08-20 02:10:45 |
| 02:30:57 | 16278807755 | 08-20 02:26:12 |
| 02:43:10 | 16278807775 | 08-20 02:39:47 |
| 02:48:50 | 16278807711 | 08-20 02:43:13 |
| 02:49:12 | 16278807766 | 08-20 02:31:00 |
| 02:53:58 | 16289232646 | 08-20 02:49:15 |
| 02:59:45 | 16299273909 | 08-20 02:54:01 |

网关每撞一次 6004 就「切号」，把整池账号的 glm-5.3 频率额度挨个烧光 → 02:59 全池耗尽 →
连续报「无可用账号」。但这是暂时的：频率限制约 1-1.5h 自恢复，实测 03:47 起 glm-5.3 已恢复。

### 6020 排队等待（2026-08-19 新观测）

返回体：

```json
{"code":6020,"msg":"queue.waiting.title","requestId":"...","data":{"queue_position":504,"queue_size":504,"retry_after":40,"estimated_wait":2520,"client_user_type":"free"}}
```

特性（实测）：

1. **模型级队列**：全池账号排的是同一个队（kimi-k3-1 的队），换号后 `queue_position`
   反而往后涨（实测 504→534）——排队状态下**切号是负效果**，换号排得更靠后。
2. **排队人数不定**（1 到 1000+ 都可能），不能靠 `queue_position` 判断，只能当独立
   「排队」类型处理。
3. **属限流的一种**：网关按账号×模型记 `queue` 冷却（探测制，同 6004），探测时用
   被排队的模型发真实请求验证，通了才解除。
4. **无号可用时透传**：全池都不可用时把排队信息透传给客户端（「无号可用，请查看日志」），
   由客户端决定稍后重试或换模型。

## 四、能否查询「单个模型每日配额」？

**不能。** 上游三个额度接口都是账号级聚合，没有任何单模型配额字段：

| 接口 | 返回内容 |
|------|---------|
| `get-user-resource`（拉资源包） | 套餐包 credits（`CycleCapacitySizePrecise`/`RemainPrecise`），聚合所有模型 |
| `get-dosage-notify`（拉用量） | `dosageNotifyCode` / 中文/英文提示文案，无模型维度 |
| `get-payment-type`（拉套餐） | `paymentType`（free / pro 等） |

单模型配额**只能被动观测**：撞限时 6004 错误消息里带的「重置时间」是唯一线索，隐含了
窗口长度（约 24h）。既查不到也不该主动轮询——只有真实请求撞上去才知道。

## 五、当前分类逻辑与上游实际不匹配（问题根因）

`src/proxy/proxy_server.py` 现状：

```python
QUOTA_ERROR_CODES = {14018}   # 额度耗尽（body code）—— 正确，14018 确为账号耗尽
QUOTA_STATUS_CODES = {429}    # 额度耗尽（HTTP 429）—— 错误，一刀切
```

`_classify_upstream_error` 的执行顺序：`11140`→banned，`14018`→quota，然后
`status_code in {429}` → 直接 `quota`，**完全没看 body 的 `6004`**。

造成的后果链：

1. `6004` 被误判为「额度耗尽」→ `mark_disabled("quota")` → **无限期限流（until=None，探测制）**
2. 网关切账号，但换号后仍用 glm-5.3 → 又撞 6004 → 连锁切号烧光整池
3. 探测制里，quota 号每次请求都被拉出来用**被限的 glm-5.3**探测 → 又白撞 6004 → 重复切号
   （实测 03:10:20 / 03:10:40 两条相同的 `switch 16501302824 → 16501302674`）

## 六、结论与修复方向

1. **429 只代表「请求过多」**，业务语义要看 body 的 `code`，不能只看 HTTP 状态码。
2. **`6004` = 单模型限流** → 应**同账号换模型**重试（glm-5.3 → glm-5.2 / deepseek-v4-flash），
   而不是切账号；切账号后继续用同一模型仍会撞限。
3. **`14018` = 账号额度耗尽** → 保持现有 `quota` 判定（已正确），切账号 / 探测恢复。
4. **探测（probe）也应避开被限模型**：限流号探测若继续用 glm-5.3，永远验证不过、永远白撞。
5. 验证方法（可复用）：直接用 `src/proxy/api_client.py` 的 `build_headers` 对
   `https://copilot.tencent.com/v2/chat/completions` 发 `stream=true` 的最小请求
   （`{"model": X, "messages":[{"role":"user","content":"hi"}], "max_tokens":3}`），
   读 HTTP 状态码 + 返回体 `code` 即可判断某账号某模型的状态（6004=单模型限流 /
   14018=账号耗尽 / 11140=封号 / 200=正常）。
