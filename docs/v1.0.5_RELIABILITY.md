## 一、窗口装饰：frameless 窗口的拉伸与白边

### 1.1 为什么 frameless 窗口不能拉伸

pywebview 的 `frameless=True` 在 Windows 上等价于 WinForms `FormBorderStyle.None`，
会同时去掉 `WS_CAPTION` 和 `WS_THICKFRAME`，而后者才是「可拉伸边框」的来源。

关键在于 pywebview 里这两个参数是**先后两段独立代码**：

| 位置 | 代码 | 效果 |
|------|------|------|
| `winforms.py:231` | `if not window.resizable: FormBorderStyle = FixedSingle` | `resizable=True` 的语义只是「**别去动** FormBorderStyle」 |
| `winforms.py:269` | `if window.frameless: FormBorderStyle = None` | 在上面之后**无条件覆写** |

frameless 永远赢，`resizable=True` 沦为空参数。**不存在任何参数组合能同时拿到
无边框和可拉伸**，后端里也搜不到任何 `WM_NCHITTEST` / `WM_NCCALCSIZE` 处理。

官方那边最接近的是 PR [#1645](https://github.com/r0x0r/pywebview/pull/1645)（纯 JS
捕获鼠标事件 + `window.resize()`），已确认**未进 6.2.1**（grep `easy_resize` 无结果）。

### 1.2 白边的两个来源

补回 `WS_THICKFRAME` 恢复拉伸后出现顶部亮边，成因是**两条叠加**：

| # | 成因 | 粗细 | 解法 |
|---|------|------|------|
| 1 | `WS_THICKFRAME` 带来的非客户区，无 `WS_CAPTION` 可画，DWM 用系统框架色填充 | ~8px | `WM_NCCALCSIZE` 子类化把非客户区清零 |
| 2 | pywebview 在 `shadow=True`（默认）时调 `DwmExtendFrameIntoClientArea(MARGINS 1,1,1,1)`（`winforms.py:169-184`），把 DWM 框架往客户区延伸 1px 并由 DWM 渲染 | 1px | `create_window(shadow=False)` |

**注意先后关系**：单独试 `shadow=False` 看不出效果，因为当时更粗的第 1 条把细线
盖住了；单独清零非客户区则会剩下那条 1px 白线。**两者必须同时用。**

### 1.3 为什么清零非客户区不影响拉伸

这是本方案的关键，也是最容易误解的地方 —— **几何与语义由两条不同的消息决定**：

| 消息 | 决定什么 | 依据 |
|------|---------|------|
| `WM_NCCALCSIZE` | client rect 放哪 = 非客户区多厚 = DWM 画什么 | 系统提议的窗口矩形 |
| `WM_NCHITTEST` | 每个像素的语义（`HTLEFT`/`HTTOP`/`HTCLIENT`…）= 拖动是否触发 sizing | **窗口矩形 + 样式位，不看 client rect** |

默认情况下二者绑在一起（有圈才有拉伸）。做法是把它们**解耦**：`WM_NCCALCSIZE`
返回 0 且不缩 `rgrc[0]` → client rect == window rect → 圈厚度为 0，DWM 无处可画；
而 `WS_THICKFRAME` 仍在，`DefWindowProc` 的命中测试照旧把最外圈判为 `HTTOP` 等。

这是 Electron / Chromium / Tauri 处理无边框窗口的同一套配方。

**已知代价（与 Electron 一致，属预期行为）**：最外约 8px 归 Windows 做拉伸命中
测试，会盖在 HTML 内容之上 —— 自定义标题栏最顶几像素是「拉伸」而不是「拖动」。

### 1.4 最大化溢出

清零非客户区后引入的**副作用**（不是原有 bug）：最大化时系统故意把窗口矩形撑到
「工作区 + 边框厚度」，本来由那圈非客户区吸收。圈没了，client rect 就会四边各
溢出屏幕约 8px。

修法：在 `IsZoomed` 分支里按 Windows 当初用来膨胀的**同一指标**缩回去 ——
`SM_CXSIZEFRAME + SM_CXPADDEDBORDER`，向系统查而非硬编码 8（不同 DPI 下不同）。

### 1.5 已排除的弯路（别再试）

| 尝试 | 结果 |
|------|------|
| 只用 pywebview 参数 | 不可能，见 1.1 |
| `shadow=False` 单独用 | 白边照旧（更粗的那条盖着），且白丢投影和 Win11 圆角 |
| `DWMWA_BORDER_COLOR = DWMWA_COLOR_NONE` | 白边仍在，**还会连带去掉 Win11 圆角** |

圆角改为**显式**声明 `DWMWA_WINDOW_CORNER_PREFERENCE = DWMWCP_ROUND`，不再依赖
系统默认推断（改过样式和非客户区之后推断结果会变）。

### 1.6 实现要点

`src/gui/win_chrome.py`，三个函数按序调用：

```
enable_resize_border()  →  suppress_nc_frame()  →  set_rounded_corners()
```

| 要点 | 说明 |
|------|------|
| **WNDPROC 防 GC** | 回调对象存进模块级 `_wndproc_refs`。一旦被 GC 回收，窗口过程指针成野指针，**下一条窗口消息直接把进程打崩** |
| 幂等 | `suppress_nc_frame` 用 `_old_wndproc` 判重，避免重复子类化套娃 |
| 异常不穿回 Win32 | WndProc 内 try/except，异常时退回 `CallWindowProcW` |
| `argtypes/restype` | 全部显式声明。ctypes 默认按 `c_int` 处理，x64 下 HWND 会被截断；`LRESULT` 用 `c_ssize_t` 取指针宽度 |
| 32/64 位分支 | 32 位 Windows 没有 `GetWindowLongPtrW` 导出符号（它是宏） |
| hwnd 查找 | `FindWindowExW` 轮询 + `GetWindowThreadProcessId` 校验 PID。原先 `time.sleep(1.5)` 后单次 `FindWindowW` 是竞态，慢机器/打包后会静默失效 |

窗口控制（最小化/最大化/关闭）改用 pywebview 官方 `minimize()`/`maximize()`/
`restore()` —— 官方实现内部走 `Form.Invoke` **编组到 UI 线程**，而 js_api 方法
本身跑在别的线程上，原先裸调 `ShowWindow` 是跨线程操作窗口。

## 二、代理链路：三处「请求永不返回」

### 2.1 根因：全链路没有墙钟超时

这是最严重的一条，也是最容易被误判为「已经设了超时」的地方：

```python
timeout=httpx.Timeout(60.0, connect=10.0, read=60.0)   # proxy_server.py
```

**httpx 的 `read` 是「单次 socket 读取」的间隔超时，不是总时长。httpx 根本没有
total timeout 的概念。** uvicorn 也没有请求级超时（`timeout_keep_alive` 只管空闲
keep-alive）。

而 `_normalize_text_stream` 会把 SSE 注释行静默跳过：

```python
if stripped.startswith(":") or not stripped:
    continue
```

**结论**：上游只要每 <60s 发一个 `: ping\n` 心跳字节，`read` 超时永不触发，
`async for` 永不结束 —— 流式连接一直开着，非流式 `await` 永久阻塞。

### 2.2 三处问题与修复

| # | 问题 | 触发条件 | 修复 |
|---|------|---------|------|
| A1 | 无总时长上限，慢速滴字即可永久挂起 | 上游持续心跳/超长思考链慢速吐字 | `STREAM_DEADLINE = 600s`，在重试循环入口与 `_normalize_text_stream` 每个 chunk 处检查，超时补 `[DONE]` 收尾 |
| A2 | peek 阶段退出条件**全是字节量**，无时间条件 | 上游先发心跳再长时间思考 | `PEEK_TIMEOUT = 25s`，超时按正常数据放行，先让客户端见到内容 |
| A3 | 已 `yield` 给客户端后仍 `continue` 换号重发 | 流中途 read timeout | `sent_any` 标志，已发内容则就地发一帧错误 + `[DONE]` 返回，禁止重试 |

A3 的实际危害比听起来严重：流式客户端收到「半个回答 + 一个完整回答」拼接；
**非流式更糟** —— `content_parts.append` 会把两次正文拼进**同一条 message**，
静默产生错误内容。回归测试实测旧代码正文变成 `'前半段完整回答'`。

### 2.3 故障转移失效（两处，比死循环更隐蔽）

| # | 问题 | 后果 | 修复 |
|---|------|------|------|
| D1 | `_first_event_kind(chunk)` 只对**单个 chunk** 解析 | SSE 错误事件被切在 8KB chunk 边界上时，两半 `json.loads` 都失败 → 14018/429 检测不到 → **不换号**，错误体原样透传给客户端，故障转移形同虚设 | 改为对累积文本 `"".join(buffered)` 解析 |
| D2 | `httpx.ConnectError` 分支是 `break` 且不 `mark_disabled` | 单个账号连不上就**放弃整轮**，完全没有故障转移 | 改为 `mark_disabled("transient")` + `continue` |

另有一处次要缺陷：`max_attempts = max(count_usable(), 1)` 在账号池未加载时算出 1
（`get_next` 才会触发 `reload`），明明有 N 个号也只试一次就 503。新增
`ensure_loaded()` / `count()`，先加载再算重试上限。

### 2.4 调度侧修复

| 问题 | 说明 | 修复 |
|------|------|------|
| `_refresh_estimates` 整体裸奔 | `calc_totals` 对 `quota_raw` 里 `{"data": null}` 会抛 `AttributeError`（配额接口报错时的真实形状）。一个账号失败会让**其后所有账号**缺失估算值，而 `deduct_quota` 对缺失 key 直接 `return` → 永不扣减、永不触发阈值 | 逐账号 try/except，失败兜底为 0 |
| `deduct_quota` 缺失 key 早退 | 同上 | 改为 `setdefault(0.0)` 而非 `return` |
| 锁内做同步 sqlite 写 | `with self._lock` 内调 `store.upsert_account` / `add_log`，sqlite 默认 `timeout=5s`，GUI 并发写库时会连带卡住这把锁和事件循环 | 落库移到锁外，锁内只做内存判定 |
| `_threshold_no_fallback` 不复位 | 成功换号后未复位，导致首次 nofallback 之后所有提示被静默吃掉 | 换号成功时复位 |
| `add_log` 裸调 | `database is locked` 会从生成器穿出去，把一次本来能成功的请求打成 500 | 统一走 `_safe_log` 包装 |

### 2.5 已确认**不存在**的风险

审计中重点排查、结论为安全的项，附挡住它的具体表达式：

| 疑虑 | 结论 | 依据 |
|------|------|------|
| 阈值换号 A→B→A 震荡 | **不会** | 备选筛选要求 `_estimated_remain.get(a.id,0) >= self._threshold`，不会切到立刻又触发阈值的号；被换下的号是 `status="disabled"` **持久化禁用**而非冷却，永久出池。每次切换永久消耗一个账号，最多 N 次 |
| 重试循环原地打转 | **不会** | 所有 `continue` 分支都先 `mark_disabled`，三种 reason 冷却均 > 0，`_is_usable` 对 `until > now` 返回 False，单调收敛 |
| 全部禁用时不退出 | **不会** | `for _attempt in range(max_attempts)` 有界；`get_next` 内层亦为 `for _ in range(n)`；返回 None → `break` → 输出 `no_account` + `[DONE]` |
| `gen.aclose()` 漏调 | **不会** | `_non_stream_chat` 的 `try/finally` 覆盖所有出口，含 try 内 `return` 与 `CancelledError` |
| 冷却内存/DB 长期不一致 | **不会** | `_restore_cooldowns` 只恢复 `until > now`；`_persist_cooldowns` 全量重写，下次任意 `mark_disabled` 即自愈 |
| 递归 / `while True` | **无** | 唯一自调用是 `get_next → reload`，深度恒为 1；`RLock` 重入安全 |

### 4.2 覆盖的切号核心语义

| 概念 | 验证内容 |
|------|---------|
| 粘性锁定 | 20 次取号全是同一个；冷却后才切走；切过去重新粘住新号 |
| 冷却分级 | quota 3600s / auth 600s / transient 60s，常量值一并断言 |
| 冷却到期 | 自动回池、记录清除 |
| 冷却持久化 | 写入 settings、新实例恢复、**过期的不恢复** |
| 永久排除 | banned / disabled / token 过期；`count_usable` 3 个号只算 1 个 |
| 阈值换号 | 切到额度充足备选；被换下的号**落库**为 disabled |
| 不震荡 | 切换次数 ≤ 账号数；无号被换下两次 |
| 无备选 | 不切号、不误禁用、只提示一次 |
| 优先账号 | 立即生效 + 重启恢复 |
| 全部不可用 | 第一次调用即返回 None，不空转 |
| `quota_raw` 往返 | 该字段一丢，`calc_totals` 全返 0，**阈值换号会静默失效** |
| 脏数据隔离 | `{"data": null}` 写入真实库后 reload 不崩，坏账号之后的账号估算值仍正常 |
| 并发 | 6 线程 × 200 次取号扣减，无死锁、扣减总量精确 |

## 五、对 v1.0.4 审计的修正

`docs/v1.0.4_AUDIT.md` 有三条结论需要修正：

| 原结论 | 修正 |
|--------|------|
| 「RLock 可重入 \| 持锁期间仅内存操作 + **微秒级 SQLite 写**，无网络 IO」 | sqlite 写并非微秒级保证 —— 默认 `timeout=5s`，GUI 并发写库时锁内可阻塞至 5 秒。已把落库移出锁外 |
| 「`_stream_inner` 重试有界 \| `max_attempts = max(count_usable(), 1)`，不会无限循环」 | 循环有界的结论正确，但漏了：池未加载时 `count_usable()` 返回 0，重试次数被算成 1，有 N 个号也只试一次。已加 `ensure_loaded()` |
| 「不阻塞 / 不死锁 / 不需重启」 | **不死锁成立，但不等于不挂起。** 当时未检查墙钟超时缺失，慢速心跳上游可让请求永久不返回。已加 `STREAM_DEADLINE` / `PEEK_TIMEOUT` |

原审计对**调度语义**的结论（粘性、冷却分级、持久化、最后号保护、无备选不死循环）
经本次回归测试逐条复核，**全部成立**。
